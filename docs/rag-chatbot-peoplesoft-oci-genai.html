Building a RAG Chatbot for PeopleSoft with OCI GenAI Agent

A proof-of-concept that extends a delivered PeopleSoft PICASO/ODA chatbot with a document-grounded question-answering agent — built on OCI's GenAI Agent service, a Function wrapper, and API Gateway — without asking PeopleSoft or ODA to speak the GenAI SDK directly.

Overview

PeopleSoft ships with PICASO, a digital assistant built on Oracle Digital Assistant (ODA), that already answers a useful set of employee questions — absence balances, benefits, team lookups, paycheck summaries. What it can't do out of the box is answer open-ended questions against your own documentation: "what does the runbook say about X," "how do I request Y." That's the gap a Retrieval-Augmented Generation (RAG) agent fills — a knowledge base built from your own documents, paired with a large language model that answers strictly from what's in it, rather than from general training data.

This project proves that pattern end to end on OCI: a knowledge base built from Object Storage documents, an OCI GenAI Agent to answer questions against it, and a path that lets both Oracle Digital Assistant and the PeopleSoft chatbot widget call it — while keeping OCI-specific authentication and SDK logic completely out of ODA and PeopleSoft.

Architecture

The core design decision was to never let ODA or PeopleSoft talk to the OCI GenAI Agent Runtime directly. Doing so would mean pushing OCI request signing, resource principal authentication, and session-management logic into ODA's skill flows — not a clean integration pattern, and a maintenance burden every time the underlying SDK changes. Instead, everything OCI-specific sits behind a Function that exposes one simple thing: a REST endpoint.

PeopleSoft / PICASO chatbot → Oracle Digital Assistant (ODA) skill → ODA REST Service → OCI API Gateway → OCI Function (wrapper / orchestrator) → OCI GenAI Agent Runtime → Object Storage knowledge base → Natural-language answer, returned all the way back

Every component above the Function line only ever calls a plain HTTPS REST endpoint. All of the OCI SDK complexity — signing requests, creating a runtime session, calling the Agent, shaping the response — lives inside the Function, where it can be changed without touching ODA or PeopleSoft at all.

The chatbot foundation

Before any of the GenAI work started, the delivered PICASO/ODA chatbot itself had to be fully working — and getting there surfaced a dependency that isn't obvious from the chatbot UI. An early symptom was a generic "Oops! Something went wrong while connecting to PeopleSoft" error on employee-lookup questions, even though backend logs showed authentication succeeding cleanly (ParseStatus: true, Authorized: true, ProcessSuccess: false).

The Employee Directory skill doesn't query a table directly — it routes through PeopleSoft's Search Framework, which depends on an OpenSearch instance running alongside PeopleSoft, plus a working Integration Broker Gateway callback:

Chatbot / ODA → PeopleSoft Application Service → Employee Directory Service → Search Framework / OpenSearch → Integration Broker Gateway callback → Response back to chatbot

If OpenSearch isn't running, the Search Instance configuration is wrong, or the Gateway callback URL doesn't match the active PeopleSoft HTTPS endpoint, the chatbot authenticates fine and then fails anonymously at the processing step — which is exactly the failure mode observed. The fix was validating OpenSearch was up and listening on its port, confirming the Search Instance host and callback URL matched the current PeopleSoft HTTPS setup, and correcting the Integration Broker Gateway URL to point at the listening connector rather than a stale service connector. A separate, smaller issue — a chatbot user missing the required Payroll Assistant role on their PeopleSoft profile — turned out to be its own independent blocker for paycheck-related questions specifically.

Takeaway: a chatbot that authenticates successfully but still fails generically is a strong signal to look at its backend dependencies — Search Framework, Integration Broker, or a missing role grant — before assuming the chatbot configuration itself is wrong.

With that foundation working, delivered PICASO flows for absence, benefits, team lookups, and paycheck summaries all validated cleanly, and — worth calling out directly — the paycheck flow correctly scoped results to the logged-in user: typing another employee's ID in chat did not return that employee's data, it returned the logged-in user's own paycheck instead.

Building the RAG agent

With the chatbot foundation solid, the RAG agent itself came together in a standard OCI GenAI Agent pattern:

  • Object Storage bucket holding the source documents the agent should answer from.
  • Knowledge base created against that bucket, with ingestion run to index the documents' content.
  • GenAI Agent configured with the knowledge base as its RAG tool, plus guardrails to keep answers grounded in the ingested content.
  • Agent endpoint created and validated directly in the OCI Console's chat interface before anything external tried to call it — proving the RAG behavior in isolation first.

One naming clarification mattered enough to call out explicitly partway through the project: this OCI GenAI Agent, wired to a document knowledge base, is a RAG Agent — its job is grounded question-answering, nothing more. A separate concept, a GenAI Agent in the action-oriented sense (reasoning over live transactional data, taking multi-step actions), is a different architecture with different security requirements. Keeping that distinction explicit early avoided scope creep later, when a reasoning-over-live-data experiment did come up.

The function wrapper pattern

Calling the GenAI Agent Runtime from a Function turned out to need its own short list of OCI plumbing, each piece easy to get wrong once:

  • Resource principal authentication. The Function authenticates to the GenAI Agent Runtime as itself, using OCI's resource principal signer — no embedded credentials.
  • A Dynamic Group matching the Function. The first matching rule used the compartment name where OCI's resource.compartment.id actually expects the compartment OCID — an easy mix-up, and one that fails silently as an authorization error rather than a clear validation message.
  • An IAM policy granting that Dynamic Group permission to invoke the GenAI Agent Runtime.
  • An OCI Container Registry (OCIR) repository to host the Function's container image, since Fn defaults to Docker Hub if its registry context is left blank — a default that produces a confusing "access denied" push error rather than an obviously wrong-registry message.

The Function itself is deliberately small — parse the incoming message, authenticate, open a session against the Agent endpoint, forward the question, and shape the response:

signer = oci.auth.signers.get_resource_principals_signer() client = oci.generative_ai_agent_runtime.GenerativeAiAgentRuntimeClient( config={}, signer=signer ) session = client.create_session( create_session_details=oci.generative_ai_agent_runtime.models.CreateSessionDetails( display_name="oda-wrapper-session" ), agent_endpoint_id=agent_endpoint_id ).data chat_result = client.chat( agent_endpoint_id=agent_endpoint_id, chat_details=oci.generative_ai_agent_runtime.models.ChatDetails( user_message=user_message, session_id=session.id ) )

Two smaller but real errors showed up during this build worth documenting: the OCI GenAI Agent SDK's response objects aren't natively JSON-serializable, so the Function has to extract plain fields before returning them (a raw Message or MessageContent object thrown straight into json.dumps fails); and OCIR authentication uses an OCI Auth Token as the Docker password, in the format <tenancy-namespace>/<oci-username> — not the regular OCI Console password, which is a distinct credential entirely and the most common reason a working docker login is followed by a failing docker push.

Exposing it through API Gateway

With the Function working end to end from a direct fn invoke, the last piece was giving ODA a plain REST endpoint to call. API Gateway sits in front of the Function, exposing a single route:

POST /psft-genai/ask { "message": "What is OpenSearch?" }

The IAM policy for this is a single line — Allow any-user to use functions-family in tenancy where request.principal.type = 'ApiGateway' — scoped down further in a production deployment, but sufficient to prove the pattern for this proof of concept. On the ODA side, a REST Service definition points at the API Gateway endpoint, and a small three-state skill flow — ask the question, call the service, display the response — completes the loop. The field name in the request body matters more than it looks: the Function expects message specifically, and a payload using question instead fails to route with a generic missing-field error.

End-to-end result

The full path validated in stages — first from PowerShell directly against the API Gateway endpoint, then from inside an ODA skill preview, and finally from the actual PeopleSoft chatbot widget, asking a knowledge-base question and getting an answer generated from the ingested documents:

PeopleSoft chatbot → PICASO/ODA → custom RAG skill → ODA REST Service → OCI API Gateway → OCI Function → OCI GenAI Agent Runtime → Object Storage knowledge base → answer returned to the chatbot

One real, honestly-documented limitation: the conversation flow itself needs polish. After one RAG question and answer, the chatbot session tends to route back into PICASO's main assistant flow rather than staying in a natural back-and-forth. That's a conversation-design gap, not a backend integration failure — the technical path proved out; the UX around it is future work.

Security notes & what's next

A natural next question once RAG worked was whether the same Function could support action-oriented reasoning, not just document Q&A — for example, comparing two paychecks and explaining why net pay changed. A plumbing experiment confirmed the routing pattern works: the same Function endpoint can branch on an action field and handle a paycheck-comparison request alongside its default RAG path, calculating the difference between two sample paychecks and returning a plain-English explanation.

What that experiment did not prove — and this distinction matters — is dynamic, secure data access. The paycheck data used was fixed sample data, not a live pull from PeopleSoft for the logged-in user, so this should be described honestly as a "plumbing experiment," not completed functionality. It surfaced the actual next challenge clearly: reasoning over data is the easy part once an LLM is in the loop; secure, user-scoped access to that data is the hard part, and it's the priority for any future iteration.

The design requirement going forward: the delivered PICASO Payroll Assistant already scopes paycheck access correctly — a logged-in user can only ever retrieve their own data, even if they type someone else's employee ID into the chat. Any GenAI extension has to preserve that exact behavior. The backend must resolve "my paychecks" from the authenticated session, and must never trust an employee ID typed into free-form chat text as authorization to return that employee's data. That's a hard requirement, not a nice-to-have, before a paycheck-comparison feature is anywhere near production-ready.

Production hardening beyond this proof of concept would also need: authenticated (not open) ODA REST service calls, least-privilege IAM policies scoped tighter than the tenancy-wide policy used here, and care around what gets written to logs given the sensitivity of payroll data flowing through the pipeline.

Summary

A working RAG chatbot for PeopleSoft comes down to one architectural discipline: keep every OCI-specific concern — authentication, SDK calls, session management — behind a Function wrapper, and let ODA and PeopleSoft talk to nothing more complex than a REST endpoint. That pattern proved out cleanly for document-grounded Q&A, end to end from PeopleSoft's own chatbot widget. Extending the same pattern to reasoning over live, user-specific data is a real next step, but it comes with a security bar that has to match what the delivered PeopleSoft chatbot already gets right: never trust an identifier typed in chat over the authenticated session it actually came from.
