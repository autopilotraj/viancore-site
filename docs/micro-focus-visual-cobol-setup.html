Setting Up Micro Focus Visual COBOL for PeopleSoft

Installing and licensing the Visual COBOL Development Hub, and the recurring errors that show up when compiling PeopleSoft's COBOL programs on Linux — collected across several real installs.

Overview

PeopleSoft still ships a set of COBOL programs (payroll, year-end processing, and similar) that require a COBOL runtime to compile and execute. Micro Focus Visual COBOL Development Hub is Oracle's supported compiler for this on Linux. The install itself is straightforward; nearly all of the friction is in licensing and in a handful of missing OS packages that the installer doesn't always surface clearly.

Installing the Development Hub
  • Copy the installation media to the target Linux server and unzip it as root.
  • Grant execute permission to the setup binary: chmod +x setup_visualcobol_devhub_4.0_patchupdate04_<build>_redhat_x86_64
  • Launch the installer, passing the admin ID that will own the Enterprise Server configuration: ./setup_visualcobol_devhub_4.0_patchupdate04_<build>_redhat_x86_64 --EsadminID=psadm2
  • Accept the EULA when prompted. The installer validates the platform, extracts its payload, and installs to /opt/microfocus/VisualCOBOL by default.
  • If you're on a newer OS release, you'll likely be missing a few 32-bit compatibility packages the installer expects — see Known Issues below before you run it, to save yourself a second pass.
Licensing

Licensing is the part most people get stuck on, mainly because it's a separate tool from the installer itself.

  • Start the License Administration tool as root: /var/microfocuslicensing/bin/cesadmintool.sh
  • Check status first — a fresh install should report No licenses found.
  • Copy your temporary (typically 30-day) or permanent license file to the server, then choose option 4, "Manual License Installation," and point it at the license file's path.
  • Re-check status to confirm the license is active — a temporary license will show days remaining; a permanent one shows Full with no expiry.
  • When you receive your permanent license, repeat the manual installation step against the new file to replace the temporary one.

If licensing later fails with "Cannot communicate with licensing daemon" — in either sample or online COBOL programs — check that the daemon is actually running with /var/microfocuslicensing/bin/mfcesdchk, and start it with /var/microfocuslicensing/bin/startmfcesd.sh if it isn't. If the daemon still won't come up, the underlying Sentinel RMS license manager service itself may be down — start it with startlserv.sh in the same directory.

Setting the COBOL environment

Set $COBDIR for the PeopleSoft OS account on every login by adding it to that account's .bashrc:

export COBDIR=/opt/microfocus/VisualCOBOL export PATH=$COBDIR/bin:$PATH

Confirm it's picked up with echo $COBDIR before moving on to compilation.

If you're on a single-user DPK deployment, one OS account owns PS_HOME, PS_APP_HOME, and PS_CFG_HOME, so you only need to set this once. Multi-user deployments — where different accounts own different homes — need the same variables set for every account that will compile COBOL, which is a common source of "it compiled tools but not app" confusion.

Compiling and relinking COBOLs

Before compiling, back up the delivered PS_HOME and PS_APP_HOME SRC and CBLBIN folders — if a compile goes wrong partway through, you want a clean starting point rather than a partially-converted source tree.

From $PS_HOME/setup, the two scripts that matter are pscbl.mak (compile) and psrun.mak (relink):

pscbl.mak PS_HOME # compile PS_HOME cobols only pscbl.mak PS_APP_HOME # compile the application's cobols only pscbl.mak # compiles PS_HOME, then PS_APP_HOME, then PS_CUST_HOME

A typical run converts every copy library and program to Unicode first, then compiles:

Start of compilation in PS_HOME (/apps/psft/pt/ps_home) ... All COBOL files were converted for Unicode successfully ... Compiling PTPCBLAE.cbl ... ... All COBOL programs have been successfully compiled. ... The COBOL executables were copied to /apps/psft/pt/ps_home/cblbin End of compilation in PS_HOME

Run psrun.mak the same way afterward to relink. If you run pscbl.mak with no home specified and you don't have any custom COBOL programs, you'll see errors about a missing PS_CUST_HOME/src/cbl directory — that's expected and not a problem if you genuinely have no custom COBOLs.

Known issues
Issue — Relinking fails on missing prerequisites

Relinking COBOLs fails with errors in psrun.err pointing at missing build tools. Installing the glibc-*.x86_64 and gcc*x86_64 packages for your architecture resolves it.

Issue — Development Hub install fails on package check

The installer aborts with a message that required 32-bit software wasn't detected — commonly glibc-devel (i686) on newer Red Hat/OEL releases that default to 64-bit-only package sets. Install the missing package explicitly, e.g. sudo yum install glibc-devel.i686, and re-run. To avoid this entirely, install the following before you start: glibc-*.i686, libgcc-*.i686, libstdc++-*.i686, glibc-devel-*.i686, gcc*x86_64, and cpp*x86_64, plus the pax archiving utility and an X11 terminal emulator if they're not already present.

Issue — License daemon unreachable

Both sample and online COBOL programs fail with a licensing communication error. Confirm the daemon is running with mfcesdchk; if not, start it with startmfcesd.sh, and check the underlying Sentinel RMS license manager service (startlserv.sh) if the daemon itself won't come up.

Issue — Java errors launching the license admin tool as root

The License Administration tool can throw Java errors when launched as root if $JAVA_HOME points at the PeopleTools-bundled JRE path rather than a real JDK. Point JAVA_HOME at an actual JDK install and add it to PATH before launching:

export JAVA_HOME=/apps/psft/pt/jdk export PATH=$JAVA_HOME/bin:$PATH

A note on multi-user setups: earlier revisions of this process required compiling PeopleTools COBOLs as one dedicated account and application COBOLs as another, since each account owned a different PeopleSoft home. Newer single-user DPK deployments don't have this split — the same account owns every home, and one round of pscbl.mak / psrun.mak covers everything. If you're still on a multi-user layout, be prepared for exactly this kind of permissions friction and plan which account compiles which home in advance.

Summary

The install itself takes minutes; licensing and missing OS packages are where the time actually goes. Install the 32-bit compatibility packages up front, understand that licensing is a separate tool from the installer, and know your account model (single-user vs. multi-user DPK) before you start compiling — that covers the vast majority of issues you'll hit.
