Multi-Cloud Terminology Cheat Sheet

A concept-organized reference for translating terminology across AWS, Azure, Google Cloud, and Oracle Cloud Infrastructure — built for interviews, architecture discussions, and reading someone else's documentation. This is a working reference, not a linear read: use the sidebar to jump straight to the section you need.

Introduction

If you know one cloud platform well, you already understand most of the ideas behind any other cloud. What changes is the vocabulary, and sometimes the design underneath the vocabulary.

This guide is organized by concept, not by provider. Look up "load balancer" or "object storage" once and see all four providers side by side, with an honest rating of how close the comparison really is.

This is not a marketing comparison, and it is not a certification study guide. It is a working reference for translating terminology quickly and correctly: in an interview, in an architecture discussion, or while reading someone else's documentation.

A note on accuracy: every mapping here was checked against official provider documentation (AWS docs, Microsoft Learn, Google Cloud docs, and Oracle Cloud Infrastructure docs). Stable, long-standing service names (Amazon EC2, Amazon S3, Azure Virtual Machines, and the like) are presented as known fact. Anything that changes often or gets commonly mixed up (identity and access management, current serverless and AI platform naming, encryption and key management, disaster recovery services, and recently renamed products) was checked again directly against the current official docs as of August 2026. Anywhere a mapping could not be confirmed with confidence, it is labeled "approximate: verify" instead of stated as fact.

Cloud providers rename, merge, and retire services often. Treat this as a living reference, and confirm against current official documentation before making a production decision.

How to Use This Guide
  • Find the concept, not the product name. If someone says "S3," look up "Object Storage."
  • Check the Mapping Quality label. A "Strong Match" is safe to treat as equivalent in conversation. A "Concept Only" is not: forcing that comparison will make you sound like you do not understand either platform.
  • Read the "Important Difference" note. This is usually the part that actually matters in a real design discussion or interview follow-up question.
  • Use the memory hook to lock in the term, then forget the memory hook and use the real name once you are comfortable.
  • If you already know OCI, jump straight to the OCI-to-AWS translation section below.
The Interview Translation Method

When an interviewer or a document uses a term from a cloud you do not know:

  • Translate the product name into the underlying generic concept: "EC2" becomes "a virtual machine."
  • Relate that concept to the cloud you already know ("that is like a Compute Engine VM").
  • Explain the architecture using generic language (compute, network, storage, identity) rather than memorized brand names.
  • Say out loud when something is not identical. Interviewers notice and respect a phrase like "the concept is the same, but the implementation differs in X way" far more than a confident wrong answer.
Mapping-Quality Legend

Every entry in this guide is labeled with one of three ratings. Read this before anything else in the document.

LabelMeaning
Strong MatchThe services solve essentially the same core problem in essentially the same way. Safe to treat as a direct mental equivalent in conversation.
Closest MatchThey solve a similar problem, but the architecture, scope, deployment model, or capabilities differ enough that you should not assume feature parity.
Concept OnlyThe general idea exists in every cloud, but forcing a specific product-to-product mapping would be misleading. Compare the concept, not the product.

If a provider has no reasonable equivalent at all, this guide says so directly: "No direct equivalent." Nothing is invented to fill a gap.

Detailed Terminology Guide

Kept in the same order as the master tables above, but with full explanations, "Important Difference" notes, and the official documentation each mapping was checked against.

1. Cloud Fundamentals

Before compute or storage, every provider has a way of organizing where your resources physically live (regions, zones) and who owns them administratively (accounts, projects, tenancies). Get this vocabulary solid first -- it is the scaffolding everything else hangs on.

Region

A geographic area (e.g., "US East," "UK South") containing multiple isolated data-center facilities. All four providers use the word "Region" the same way. Mapping Quality: Strong Match. Memory trick: Region = the city/metro area. Important difference: the number and geographic footprint of regions differs a lot between providers -- always check current availability for your workload before assuming a region exists.

Availability Zone / Availability Domain

An isolated failure domain inside a region: its own power, cooling, and networking, so that one physical outage does not take down everything in the region. AWS and Azure call it an Availability Zone (AZ); GCP calls it a Zone; OCI calls it an Availability Domain (AD). Mapping Quality: Strong Match. Important difference: OCI historically shipped with far fewer Availability Domains per region than AWS/Azure/GCP have AZs -- some OCI regions have only 1 AD. OCI compensates with Fault Domains inside each AD. Do not assume "3 AZs" the way you might for AWS.

Fault Domain

A smaller failure-isolation boundary inside an Availability Zone/Domain -- separate racks, power, and hardware, so redundant copies of something do not fail together even within the same zone. Mapping Quality: Concept Only. OCI is the provider that leans on this concept most heavily: every OCI Availability Domain is explicitly divided into 3 Fault Domains, and OCI's own high-availability guidance assumes you spread instances across them. Memory trick: Region, then Zone/AD, then Fault Domain -- each level is a smaller box inside the last one.

Mapping Quality: Concept Only. Do not say these are the same thing, because the level at which they operate differs. An AWS Account and a GCP Project are close cousins -- both a hard billing/quota boundary, normal to have dozens. An Azure Subscription sits at roughly the same level. OCI is structurally different: a single OCI Tenancy is the root, and you organize inside it using Compartments -- logical containers with no billing boundary of their own. A new OCI customer typically starts with one Tenancy and many Compartments, not many Tenancies. This is the single most common source of confusion moving between OCI and the other three.

Interview Translation: if someone says "we isolate environments using separate AWS accounts," the honest OCI answer is "we would use separate Compartments inside one Tenancy," not "separate Tenancies." A new Tenancy is a much bigger, rarer boundary (closer to a whole new customer relationship).

Tags vs. Labels

Metadata attached to a resource for cost allocation, ownership, environment, or automation. AWS and Azure both say "Tags." GCP uses "Labels" (and, on some newer resources, a separate IAM-integrated "Tags" concept). OCI has Free-form Tags and Defined Tags. Mapping Quality: Strong Match for the general idea, Closest Match on mechanics. Important difference: OCI's Defined Tags are schema-controlled (an administrator defines allowed keys/values in a Tag Namespace), closer to a governed taxonomy than a free-text label. GCP's "Labels" and "Tags" are two separate mechanisms -- do not conflate them.

Spot / Preemptible / Interruptible Compute

Your own isolated, software-defined network inside the provider's cloud, where you define IP ranges and place resources. Mapping Quality: Strong Match. If You Know OCI: OCI VCN is basically AWS VPC. Important Difference: GCP VPC networks are global by default (subnets span regions within one VPC); AWS VPCs, Azure VNets, and OCI VCNs are regional constructs. This is a real architectural difference, not just naming.

Subnet

A smaller IP range carved out of the VPC/VNet/VCN to organize and isolate resources. Mapping Quality: Strong Match on concept, Closest Match on scope. Important Difference: an AWS subnet lives in exactly one Availability Zone. Azure and GCP subnets are regional. An OCI subnet can be either regional (spans all Availability Domains, the modern default) or the older AD-specific style. Do not assume "subnet = one zone" outside of AWS.

Public Subnet vs. Private Subnet

A "public" subnet has a route to an internet gateway; a "private" subnet does not (it reaches the internet only through a NAT gateway, if at all). This is a routing configuration, not a distinct resource type, on every provider. Mapping Quality: Concept Only -- a private subnet is not automatically secure, see Do Not Confuse These.

Internet Gateway

AWS and OCI model this as a discrete resource you must create and route to (Internet Gateway). Azure and GCP achieve the same outcome implicitly through public IP assignment and routing/firewall rules -- there is nothing to "attach." Mapping Quality: Closest Match. 5. Identity and Access Management

This is the section most likely to be misunderstood in an interview, so read it slowly. Do not say Microsoft Entra ID = AWS IAM. They are not peers. They solve different layers of the same overall problem.

The Core Distinction: Directory vs. Authorization

Every cloud actually needs two different things, and providers package them differently: (1) a directory / identity provider -- where human users and their credentials actually live, get authenticated, and get MFA'd, i.e. "who is this person"; and (2) a cloud authorization engine -- the system that decides "now that we know who you are, what are you allowed to do on this specific cloud resource," i.e. policy evaluation, not identity.

Mapping Quality: Concept Only for the overall category; the individual layers are more precise. The corrected mapping: Microsoft Entra ID is closest, as a product category, to AWS IAM Identity Center (workforce SSO, directory integration) plus a slice of Google Cloud Identity -- it is an enterprise identity provider, not an authorization engine. AWS IAM, Azure RBAC, and Google Cloud IAM are the actual peer group: all three are "who can do what to which resource" authorization engines sitting underneath whatever directory supplies the identity. OCI is architecturally different from all three of the above, and this trips people up the most: an OCI IAM Identity Domain bundles the directory/IdP function (users, groups, federation, SSO, MFA) and the base identity object model together in one product, tied to your Tenancy. Since 2021, OCI has been progressively migrating tenancies from a legacy identity model onto Identity Domains -- someone on an older tenancy may still describe "OCI IAM" without the Identity Domains layer.

Interview Translation: if asked how Entra ID compares to AWS IAM, a good answer is: "They are not really peers. Entra ID is our identity provider, where our users and groups live and get authenticated. AWS IAM is the authorization layer that decides what an already-authenticated identity can do to AWS resources. The AWS product that plays in Entra ID's space is IAM Identity Center, which federates against an external directory like Entra ID."

Workforce Identity vs. Workload Identity

Workforce identity = people signing in (employees, contractors, admins). Workload identity = applications, services, and compute resources authenticating to each other, without a human typing a password.

Mapping Quality: Closest Match. Important Difference (OCI Dynamic Groups deserve their own explanation): a Dynamic Group is not a group of users at all. It is a rule-based group of OCI resources (e.g. "all Compute instances in this compartment," matched by instance metadata) that IAM policies can then grant permissions to. This lets a VM or Function call OCI APIs without embedding credentials -- the same underlying goal as an AWS instance profile or an Azure Managed Identity, just expressed as a dynamically-matched resource group rather than an identity directly attached to the resource. Resource Principals are the credential-delivery mechanism a resource in a Dynamic Group actually uses at runtime, roughly similar to how an EC2 instance uses its instance-profile role's temporary credentials, or how an Azure resource uses its Managed Identity token.

Federation and SSO

Letting users authenticate with an identity they already have instead of creating a brand-new username/password in the cloud platform. Mapping Quality: Concept Only at the category level -- universally supported, but implementation patterns vary. GCP's split into Workforce Identity Federation (humans) and Workload Identity Federation (machines and multicloud workloads) is a useful, explicit distinction AWS and Azure do not name quite as cleanly.

Temporary Credentials

Short-lived access credentials issued to a role, workload, or federated session -- the modern best practice everywhere. Mapping Quality: Concept Only. AWS STS, Azure Managed Identity short-lived tokens, GCP short-lived service account credentials, and OCI Resource Principals all converge on "do not use long-lived static keys."

Network Firewall vs. Security Group vs. WAF

Three different layers get lumped together as "security" and they are not interchangeable. A Security Group / Network Security Group is a stateful firewall attached to a specific resource, controlling what traffic can reach that resource. 7. Encryption and Key Management
What Encryption Actually Protects (and What It Does Not)

Encryption protects data confidentiality if the underlying storage or network is somehow accessed directly, bypassing your application (a stolen disk, a misconfigured public bucket, a network sniffer). It does not replace access control. If a user has valid IAM permission to read a file, encryption at rest is transparent to them -- they see the plaintext, because the service decrypts it for them. Encryption and IAM solve different problems and you need both.

ConceptSimple meaning
Encryption at restProtects stored data -- on disk, in a database, in an object store, in a backup.
Encryption in transitProtects data while it moves across a network -- usually TLS for application traffic, IPsec for VPNs.
Provider-managed keysThe cloud provider generates, stores, and rotates the encryption key for you. Simplest, but you do not directly control it.
Customer-managed keys (CMK)You create and control the key (rotation, disabling, deletion, access policy) inside the provider's KMS; the provider's service still performs the actual encrypt/decrypt using that key.

Who controls the key, and why it matters: with a provider-managed key, the provider can always decrypt your data on your behalf -- you are trusting their operational and legal controls. With a customer-managed key, you decide who and what can use the key, and can revoke that access (or delete the key) to make data cryptographically unreadable even to the provider's own service -- but now key availability is your responsibility too. Do not say customer-managed keys are simply "more secure" without qualification.

12. High Availability, Backup, and Disaster Recovery

Mixing up these terms is one of the fastest ways to lose credibility in an infrastructure interview, so read this section closely.

Three Different Concepts, Constantly Confused
  • High Availability (HA): surviving a local failure (a host, a rack, a zone) automatically, usually within seconds, without anyone declaring an incident. Achieved by spreading redundant components across Availability Zones/Domains.
  • Backup: a separate, recoverable copy of data, protecting against corruption, accidental deletion, or ransomware. A backup does not by itself restore a running service -- someone has to actually restore it.
  • Disaster Recovery (DR): the plan and tooling to bring an entire application/service back online, usually in a different region or site, after a large-scale failure. DR is orchestration on top of replicated infrastructure and/or backups -- a business-continuity capability, not a single button.

Backup is not Disaster Recovery. High Availability is not Disaster Recovery. You can have excellent backups and still have no real DR plan if nobody has practiced restoring the whole application stack, in order, within a time limit.

Common Interview Translation Examples
"What is an EC2 instance?"

A virtual machine running in AWS's cloud, you pick the CPU/memory profile (instance type), operating system image, storage, and network placement. OCI equivalent: a Compute Instance. Difference: shape catalogs, default storage behavior, and networking defaults differ.

"What is an AWS VPC?"

Your own isolated virtual network inside AWS, where you define IP address ranges and place resources into subnets. OCI equivalent: a VCN. Difference: none significant at the core concept level. This is one of the safest translations in cloud computing.

"What is S3?"

AWS's object storage service, you store files as "objects" inside "buckets," accessed over HTTP(S), not mounted like a disk. OCI equivalent: Object Storage. Difference: storage tiers and consistency details vary; the fundamental model is the same.

"What is EBS?"

Block-level storage that attaches to a single EC2 instance, like a virtual hard drive. OCI equivalent: Block Volume. Difference: IOPS/throughput provisioning models differ.

"What is IAM?"

The system that decides what an authenticated user, role, or workload is allowed to do to AWS resources, authorization, not authentication. OCI equivalent: OCI IAM policies. Difference: OCI policies are written in a distinct, human-readable statement syntax rather than JSON policy documents, and OCI's Dynamic Groups take the place of AWS's resource-attached IAM roles.

"What is an IAM role?"

A set of permissions that can be temporarily assumed by a user, application, or AWS service, rather than a permanent identity holding permissions directly. OCI equivalent: not a direct one, the closest pattern is a Dynamic Group (a rule-matched group of OCI resources) tied to an IAM policy. Difference: OCI's version is expressed as a resource-matching rule, not an assumable role object.

"What is a security group?"

A stateful, resource-attached virtual firewall controlling inbound/outbound traffic to a specific instance or network interface. OCI equivalent: Network Security Groups. Difference: OCI also has an older, subnet-level mechanism (Security Lists) that can be layered with NSGs, check which one a given VCN actually uses.

"What is a private subnet?"

A subnet with no route to an internet gateway, resources there can't be reached directly from, or reach out directly to, the public internet without a NAT gateway. OCI equivalent: a private OCI subnet, same concept. Important: a private subnet is not automatically secure by itself, see Do Not Confuse These below.

"What is a NAT Gateway?"

Lets resources in a private subnet make outbound internet connections (e.g., to download updates) without accepting unsolicited inbound connections from the internet. OCI equivalent: OCI NAT Gateway. Difference: none significant.

"What is Direct Connect?"

A dedicated network connection between your data center and AWS, bypassing the public internet for more consistent performance. OCI equivalent: FastConnect. Difference: none significant at the concept level; provisioning process and available connectivity partners differ.

"What is Multi-AZ?"

Running redundant resources across multiple Availability Zones so a single zone failure doesn't take the whole service down. This is a high-availability pattern, not disaster recovery. OCI equivalent: Multi-AD (or Multi-Fault-Domain in single-AD regions). Difference: OCI regions may have only one AD, in which case OCI achieves the equivalent local resilience using Fault Domains instead.

"What is CloudWatch?"

AWS's metrics, alarms, and log-collection service, how you observe system health and behavior. OCI equivalent: split across OCI Monitoring (metrics/alarms) and OCI Logging (logs), there isn't one single OCI product covering both the way CloudWatch does.

"What is CloudTrail?"

A record of who made what API/console change and when, across your AWS account, the control-plane audit trail. OCI equivalent: OCI Audit. Difference: none significant at the concept level.

"What is EKS?"

AWS's managed Kubernetes service, AWS runs the Kubernetes control plane; you still manage (or choose a serverless option for) the worker nodes. OCI equivalent: OKE. Difference: default networking/CNI model and node-management options differ.

"What is Lambda?"

AWS's serverless function service, you upload code, define a trigger, and AWS runs it on demand without you managing a server. OCI equivalent: OCI Functions. Difference: runtime support, cold-start behavior, and execution limits differ.

"What is RTO and RPO?"

RTO is how long you can be down before it's unacceptable. RPO is how much recent data you can afford to lose. Both are business-continuity targets that drive your DR architecture. They are not products; they're requirements you design to.

Do Not Confuse These
IAM vs. SSO

IAM decides what an already-identified entity can do to a resource. SSO is about how a person authenticates once to access multiple systems. Entra ID, IAM Identity Center, Cloud Identity, and OCI Identity Domains handle SSO; AWS IAM, Azure RBAC, Cloud IAM, and OCI IAM policies handle authorization.

Authentication vs. Authorization

Authentication answers "who are you" (login, MFA). Authorization answers "what are you allowed to do, now that we know who you are." Every IAM system on every provider is fundamentally an authorization system, even though people casually call the whole login experience "IAM."

Security Group vs. WAF

A security group filters by IP/port at the network layer and has no idea what's inside the HTTP payload. A WAF inspects the actual content of HTTP requests for attack patterns. They operate at different layers and neither replaces the other.

Security Group vs. Network ACL

A security group is stateful and attached to a specific resource/interface. A network ACL (or OCI Security List) is attached to a subnet and evaluated for every resource inside it, and can be stateless depending on the provider. Traffic to a resource is typically evaluated against both.

Object vs. Block vs. File Storage

Object storage = files accessed over HTTP(S) as named objects in buckets (S3, Blob Storage, Cloud Storage, OCI Object Storage), great for unstructured data at scale, not mountable as a filesystem. Block storage = a raw virtual disk attached to one VM (EBS, Managed Disks, Persistent Disk, Block Volume), needed for boot volumes and databases. File storage = a shared network filesystem mountable by multiple servers at once (EFS, Azure Files, Filestore, OCI File Storage), needed when several servers must see the same files simultaneously.

Internet Gateway vs. NAT Gateway

An Internet Gateway lets resources with a public IP be reached from (and reach) the internet directly, in both directions. A NAT Gateway lets resources without a public IP reach out to the internet, but nothing on the internet can initiate a connection back in. A private subnet uses a NAT Gateway, never an Internet Gateway, for its own outbound traffic.

VPN vs. Dedicated Private Circuit

A site-to-site VPN is an encrypted tunnel over the public internet, cheaper and faster to set up, but subject to internet variability. A dedicated circuit (Direct Connect, ExpressRoute, Cloud Interconnect, FastConnect) is a private, non-internet physical/logical connection, more predictable performance, but slower to provision and typically costs more.

Load Balancer vs. API Gateway

A load balancer distributes traffic across healthy backend servers/instances, usually with limited awareness of application semantics beyond basic routing rules. An API gateway is API-aware: it can authenticate callers, enforce rate limits per API key, transform requests and responses, and version APIs. Many real architectures use both together: a load balancer in front of an API gateway, or an API gateway that itself load-balances to backend services.

HA vs. Backup vs. DR

High Availability survives a local failure automatically, in seconds, with no data loss and (usually) no user-visible interruption. Backup gives you a separate, recoverable copy of data for when something is corrupted, deleted, or compromised, it does not run anything by itself. Disaster Recovery is the orchestrated plan to bring a whole application back online elsewhere after a major failure, built on top of replication and/or backups, measured against RTO and RPO targets.

RTO vs. RPO

RTO = time. "How long until we're back up?" RPO = data. "How much recent data can we lose?" A very low RTO with a high RPO means you come back online fast, but potentially missing a chunk of recent data, and vice versa. They're usually set together but they are not the same axis.

Metrics vs. Logs vs. Traces vs. Audit Logs

Metrics are numbers over time (CPU%, request count). Logs are detailed text records of events. Traces follow one request's path across multiple services to find where time was spent or where it failed. Audit logs record who took what administrative/API action, for accountability and compliance, a fundamentally different purpose than the other three, which are about system behavior, not human accountability.

Secret vs. Encryption Key

A secret is a piece of sensitive data your application needs (a database password, an API token). An encryption key is the cryptographic material used to encrypt/decrypt other data. A secrets manager stores secrets (and can itself use an encryption key to protect them at rest); a KMS manages encryption keys. Some providers (Azure Key Vault, for example) put both under one product umbrella, which makes this distinction easy to blur. Keep the two separate anyway.

Kubernetes vs. Serverless

Kubernetes gives you a persistent, configurable, always-on orchestration platform where you (or a managed control plane) decide scaling, scheduling, and networking in detail. Serverless (functions or serverless containers) hands scaling and infrastructure decisions entirely to the platform, scales to zero when idle, and typically bills per invocation/duration rather than per running node. Neither is strictly "better", they trade control for operational simplicity in opposite directions.

Availability Zone vs. Region

A Region is a broad geographic area; an Availability Zone (or Availability Domain on OCI) is an isolated failure domain inside that region. Multi-zone protects against a local outage; multi-region protects against losing an entire geographic area (and is usually part of a DR strategy, not just an HA one).

Snapshot vs. Backup

A snapshot is typically a point-in-time, often incremental copy tied closely to the underlying storage/disk system, and can be very fast to create and restore from. A "backup" (in the AWS Backup / Azure Backup / centralized-policy sense) usually adds policy-driven scheduling, retention rules, and cross-service/cross-region consistency management on top of the same underlying snapshot mechanism. In casual conversation people use the words interchangeably. In an interview, it's worth pointing out that "a snapshot exists" and "we have a governed backup policy" are not the same claim.

Account vs. Subscription vs. Project vs. Tenancy

An AWS Account and a GCP Project are peers: both are a billing/quota/identity boundary you're expected to create many of. An Azure Subscription is also a peer at that same level. An OCI Tenancy is structurally different. It's the root of everything, and you subdivide inside it using Compartments, rather than creating many Tenancies the way you'd create many AWS accounts. See the full explanation in Cloud Fundamentals.

Corrections to Common Comparison Mistakes

A lot of multi-cloud cheat sheets circulate online and in study groups, and several of them repeat the same mistakes. Below are the ones worth calling out directly, with the reasoning, so you don't repeat them either.

  1. AWS Snow Family status. Older comparison charts list "AWS Snowball/Snow Family, Azure Data Box, and OCI Data Transfer Appliance" as a stable three-way match with no caveat. Official AWS documentation confirms Snowball Edge devices have been discontinued for new customer orders, with AWS directing new customers to AWS Data Transfer Terminal (offline) and AWS DataSync (online) instead. Corrected in the Migration section.
  2. Microsoft's AI platform rebrand. Charts still floating around reference only "Azure AI Foundry" or "Azure AI Studio." Neither is current: Microsoft rebranded this platform to Microsoft Foundry in 2026. Corrected in the Data, Analytics, and AI section, with the naming history kept so readers coming from older material aren't confused.
  3. Azure Cache for Redis retirement. Older material lists "Azure Cache for Redis" as Azure's current Redis offering with no qualification. Official Microsoft documentation confirms Azure Cache for Redis is being retired on a published timeline (2027-2028 depending on tier) in favor of Azure Managed Redis, which this guide treats as the current answer.
  4. Microsoft Fabric vs. Azure Synapse Analytics. These two are often either presented as unrelated products or Synapse is written off as already gone. Neither is accurate: official Microsoft messaging confirms Synapse Analytics remains supported, but Microsoft is actively guiding customers to migrate workloads to Fabric, which is now the primary strategic data platform.
  5. A common IAM table is materially misleading. It's common to see "OCI IAM / AWS IAM / Microsoft Entra ID / Cloud IAM" listed side by side as if they were four peer products solving the same problem. They are not. Entra ID and Cloud Identity are directory/identity-provider products; AWS IAM, Azure RBAC (evaluated against Entra ID identities), and Cloud IAM are authorization engines; OCI's Identity Domains uniquely bundle both roles into one product. This guide corrects that into an explicit two-layer model, with OCI's hybrid architecture called out (Identity and Access Management section).
  6. Audit-logging comparisons are often oversimplified. It's common to see "Azure Activity Log" listed as a straight peer to AWS CloudTrail with no distinction. Official Microsoft documentation shows Azure splits this responsibility between the Activity Log (resource-management operations) and Entra ID's own sign-in/audit logs (identity events). CloudTrail, Cloud Audit Logs, and OCI Audit are each closer to a single, unified log. Corrected in the Monitoring, Logging, and Audit section.
  7. OCI's resource hierarchy is not a flat equivalence. A common memory-trick slide states "OCI Compartment = AWS Account/OU = Azure Subscription = GCP Project" as if they're interchangeable. They're not: a Compartment is a logical subdivision inside one OCI Tenancy, while an AWS Account, Azure Subscription, and GCP Project are each themselves the base billing/quota unit (closer in level to the Tenancy itself). This is corrected throughout, most fully in the Cloud Fundamentals section, because it's one of the most common real-world sources of confusion for people moving between OCI and the other three providers.
  8. AWS PrivateLink does not have a single OCI equivalent. It's common to see a rough 1:1 drawn between AWS PrivateLink/Azure Private Link/GCP Private Service Connect and an OCI "Service Gateway / private endpoint" catch-all. This guide is explicit that OCI splits this job across Service Gateway (for OCI's own public services) and separate per-service private endpoint features, with no single unifying OCI product. Labeled Closest Match rather than Strong Match, with the distinction spelled out.
  9. Google Cloud Functions naming. Material that still calls this product only "Cloud Functions" is out of date. Cloud Run functions is the current official name (Google renamed Cloud Functions and re-platformed it onto Cloud Run infrastructure). Same product line, older name.
  10. API Gateway vs. Apigee on GCP. These two get listed as interchangeable alternatives for the same job more often than not. Official Google documentation is clear they are two distinct products for two different scopes: lightweight serverless API fronting versus full enterprise API lifecycle management. Corrected in the DevOps and Application Integration section.
  11. OCI has no direct Batch or wide-column NoSQL equivalent. It's tempting to stretch and name some loosely-related OCI feature as the answer for AWS Batch/Azure Batch/Google Cloud Batch, or for AWS Keyspaces/GCP Bigtable. Per this guide's own rule (if there's no reasonable equivalent, say so), both are labeled No direct equivalent for OCI instead.
