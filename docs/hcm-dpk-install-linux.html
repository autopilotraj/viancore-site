Installing a PeopleSoft HCM Deployment Package (DPK) on Linux

A field-tested walkthrough of the Oracle DPK installer for an HCM environment on Linux — the prep steps that save you a rerun, and the prompts that are easy to answer wrong the first time.

Overview

The Deployment Package (DPK) is Oracle's standard mechanism for standing up a PeopleSoft environment — application, PeopleTools, and database — as a single scripted install driven by Puppet under the hood. It's reliable once you understand its assumptions, but it front-loads a lot of validation, and a failed prerequisite check late in the process costs you the whole extraction step over again. Getting the prep work right the first time is most of the battle.

Before you start

Before touching the installer, verify the host is actually ready for it:

  • Confirm free disk space with df -h — the DPK extracts, then deploys, so you need roughly double the archive size free.
  • Check memory and CPU against the minimums in the install guide (cat /proc/meminfo, cat /proc/cpuinfo).
  • Confirm full read/write access to /tmp and /var/tmp — several install phases stage files there.
  • Check the umask in /etc/bashrc and /etc/profile; the installer expects 022.
  • Make sure the Oracle Linux/RHEL release packages and oracle-database-preinstall-19c are installed — this pulls in most of the OS-level dependencies the DPK assumes are already there.
  • Check for glibc and install glibc-devel if it's missing.
  • Create a dedicated install directory (for example /apps/DPK_INSTALL) with permissions that let the setup script run without fighting the filesystem.
  • Two compatibility symlinks trip people up more than anything else on newer OS releases — libncursesw.so.5 and libtinfo.so.5 are often missing entirely. Either symlink them from the .so.6 versions already present, or install ncurses-compat-libs and skip the symlinks.
Running the DPK installer

Once the zip archives are unpacked and the setup script is executable, kick off the installer:

[root@host ~]# ./psft-dpk-setup.sh Starting the PeopleSoft Environment Setup Process: Validating User Arguments: [ OK ] Validating PeopleSoft Supported Platform: [ OK ] Extracting the Zip File ... [ OK ] Validating Oracle Central Inventory: [ OK ]

From here the script walks through a long, mostly linear sequence: extracting each DPK archive (application, PeopleTools client and server, and the Oracle database server/client DPKs), validating the manifest for each one, then bootstrapping Puppet and its eYAML Hiera backend, which is what actually drives the deployment.

Key decisions during setup

The installer asks a series of questions partway through. A few of them are easy to answer without thinking and hard to walk back:

  • Base directory — where the DPKs get extracted and the components deployed. Needs to be writable with real headroom; changing this later means starting over.
  • Installation type — PUM or FRESH — FRESH builds a clean environment from the delivered database; PUM is for an update-image-based refresh.
  • Database type — DEMO or SYS — DEMO loads Oracle's demo data, useful for a sandbox or training environment; SYS gives you a bare database you'll populate yourself.
  • Database name — must start with a letter, uppercase letters and numbers only, 8 characters max. Plan this in advance so it fits your naming convention.
  • A run of password prompts follows — database admin, Connect ID, Access ID, Operator ID, WebLogic Admin, Web Profile user, and Integration Gateway user and keystore. Have a password policy decided before you get here.

Once you confirm the answers, the installer encrypts everything into the Hiera YAML files and proceeds unattended through deployment: application components, the Oracle database server, PeopleTools, OS users, the database itself, and the Application Server, Process Scheduler, and PIA domains — finishing with a full stop/start cycle of the environment.

Lessons learned
  • Do the prep checklist in full before starting — the installer validates a lot up front, but not everything, and a failure two-thirds of the way through a multi-hour deployment is expensive.
  • Write down your answers to the PUM/FRESH, DEMO/SYS, and database name prompts before you start the run. There's no going back once the bootstrap begins without tearing the environment down.
  • If you want to customize the environment beyond the defaults, don't fight the prompts — answer 'n' at the final confirmation and follow the documented path for a custom psft_customizations.yaml Hiera file instead.
Summary

The DPK installer removes most of the manual PeopleSoft build process, but it front-loads the decisions that matter — base directory, install type, database naming, and passwords — into a handful of prompts you answer once. Treat the prep checklist as non-negotiable and have your answers ready before you start, and the rest of the process is close to unattended.
