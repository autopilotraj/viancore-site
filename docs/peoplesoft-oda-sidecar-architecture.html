The PeopleSoft + ODA Sidecar Pattern

A modernization option worth understanding before recommending a full re-platform: layer Oracle Digital Assistant on top of an unmodified PeopleSoft back office instead of touching the core system at all. This is an architecture and cost analysis, not a hands-on build write-up — the kind of thinking that goes into a modernization recommendation before a single line of PeopleCode changes.

Overview

Most organizations still running PeopleSoft for HCM, Financials, or Campus Solutions aren't looking to rip it out — the back-office logic is deep, accurate, and expensive to reproduce. What they're actually unhappy about is the user experience: menu navigation, page-by-page workflows, and a UI that hasn't kept pace with what employees expect from consumer software. A full re-platform to a SaaS alternative fixes that, but at a cost and risk profile that's hard to justify for the UX problem alone.

The "sidecar" pattern is the middle path: put Oracle Digital Assistant (ODA) in front of PeopleSoft as a conversational layer, talking to the existing system entirely through REST APIs, while every payroll rule, approval workflow, and finance calculation stays exactly where it is. Nothing about the pattern requires touching PeopleCode or re-certifying the back office — the risk surface is the integration layer, not the system of record.

Architecture

The core design principle is separation: PeopleSoft never has to know it's being asked a question by an AI, and ODA never touches the PeopleSoft database directly. Every interaction goes through Integration Broker, using a dedicated proxy user with exactly the permissions a real end user would have — nothing more.

The connection between the two sides is a plain secure REST/HTTPS API — Oracle Integration Cloud is the usual broker when more orchestration is needed, but the principle holds either way: the API surface is deliberately narrow, and it carries scoped responses, not raw data or bulk exports.

How a request flows
  • An employee asks a question in natural language — Teams, a web widget, or mobile — for example, "how many vacation days do I have left."
  • ODA's NLU layer resolves the intent and determines what PeopleSoft data answers it.
  • ODA calls PeopleSoft's Integration Broker over HTTPS, through a gateway/load balancer.
  • PeopleSoft authenticates the call through the dedicated proxy user, then validates the actual requesting user's own permissions — the proxy user is a transport identity, not a permissions bypass.
  • Existing PeopleCode, workflow, and approval logic runs exactly as it would for a browser session, and returns only the specific data requested — no bulk access, no direct database reads.
  • ODA converts the structured response into a natural-language answer, optionally using generative AI to summarize when the response is long-form (a policy document, for instance, rather than a single number).
  • The employee gets an answer in the same chat thread, typically within a few seconds.

Why this matters for risk: because every step routes through Integration Broker under the requesting user's actual permission set, the AI layer can't accidentally expose data the user couldn't already see through the normal UI. The chatbot is a new front door, not a new set of keys.

What the AI layer adds beyond a scripted chatbot

Oracle shipped PICASO as a pre-built PeopleSoft digital assistant for years, but the current direction — reinforced by pre-built PICASO skills now being deprecated in favor of the Chatbot Integration Framework (CIF) — is toward custom agents built directly on ODA. That shift unlocks a handful of capabilities that a scripted, intent-only bot doesn't have:

CapabilityWhat it changes
Generative AI summarizationODA can pull a document PeopleSoft holds — a policy PDF, for instance — and summarize it inline rather than just linking to it.
Natural-language data questionsA manager's plain-English question about spend or headcount can be translated into a structured query against PeopleSoft data, instead of requiring a saved query or report.
Omnichannel deliveryThe same skill can be reached from Teams, Slack, or a web widget — the back office stays put, but the interaction moves to wherever people already work.
Multilingual by defaultA question asked in one language can be understood and answered in that language even though the underlying PeopleSoft pages were never translated.
Weighing it against the alternatives

The sidecar pattern is one point on a spectrum of PeopleSoft modernization options, and the honest way to evaluate it is against the other two paths organizations typically consider. These are rough, directional ranges for a mid-size enterprise engagement — every environment's actual numbers will vary with scope, headcount, and how much technical debt already exists in the current PeopleSoft instance.

ApproachTypical cost rangeTypical timelineRelative risk
ODA sidecar on existing PeopleSoftLow six figures2–4 monthsLow — no core system changes
Lift-and-shift PeopleSoft to OCI (IaaS)Mid six to low seven figures3–9 monthsMedium — infrastructure and cutover risk, logic unchanged
Full SaaS re-platform (e.g., Oracle Fusion, Workday)Seven to eight figures12–36 monthsHigh — business process redesign, data migration, change management at scale

The gap in both cost and timeline between the sidecar approach and a full re-platform is large enough that it's worth treating them as genuinely different decisions, not points on the same roadmap. A sidecar buys UX improvement now; it doesn't buy out of an eventual re-platform conversation if the underlying PeopleSoft version itself is aging out of support.

Pricing shape & hidden costs

ODA's own pricing is usage-shaped rather than a flat per-environment fee, and the right model depends heavily on who's using it:

MetricBest fit
Named userInternal employees where headcount with access is known and stable — the common choice for HCM/Financials self-service.
Session-basedHigh-volume "guest" access where the user count is unpredictable — student applicants, external suppliers.
Request-basedLow-volume, narrowly transactional bots, though most vendors enforce a practical minimum request volume.

The license fee is also not the full production cost. Budgeting realistically means adding in the pieces that make the integration secure and usable at scale: a load balancer or API gateway to expose Integration Broker to the cloud safely, object storage if the assistant needs to read and summarize documents, and an identity service to keep PeopleSoft user accounts synchronized with the assistant's authentication. None of these are large individually, but a proposal that only quotes the per-user license fee is quoting an incomplete number.

Where the PeopleSoft environment is hosted also matters more than it first appears. ODA itself runs in OCI regardless of where PeopleSoft lives, so an on-premises PeopleSoft environment needs a private network path — a dedicated cloud interconnect or VPN — to keep latency acceptable, plus a modest egress cost for data leaving the data center. PeopleSoft hosted in another public cloud changes the calculus again: Oracle and Microsoft's direct interconnect, for instance, can bring OCI-to-Azure latency down to single-digit milliseconds and lets the identity layer piggyback on an existing Azure AD/Entra ID tenant for single sign-on, which removes a whole category of integration work.

Staffing it correctly

This is a smaller build than a re-platform, but it isn't a one-person project — it draws on four distinct skill sets, and skipping any one of them shows up later as rework:

RoleOwnsWhy it's non-negotiable
System / Security adminIntegration Broker, the proxy user, SSL, Web SDKThe proxy user's permission scoping is the entire security model — this has to be existing PeopleSoft security expertise, not a generalist.
Technical leadApplication Classes, Application Service FrameworkThis is the PeopleCode surface actually exposed to ODA — get the service contract wrong and every downstream skill inherits the bug.
DBAPerformance, search indexingA chatbot adds a new, bursty load pattern against PeopleSoft and its search index that the DBA needs to plan capacity around.
Conversation designerChat flows, intents, NLU trainingThis is where most of the actual "business logic" of a good assistant lives, and it's config, not code — a role that's easy to underestimate if the team is used to thinking in PeopleCode.
When this pattern fits

The sidecar pattern earns its place when the actual complaint is about user experience and self-service friction, not about the underlying business logic or the platform's long-term viability. It's a strong fit for reducing help-desk and call-center load on high-volume, low-complexity questions — balance lookups, status checks, directory searches — where the answer already exists in PeopleSoft and the only real problem is how many clicks it takes a person to find it.

It's a weaker fit as a substitute for addressing a genuinely aging PeopleSoft foundation. If the underlying PeopleTools release, database version, or PUM currency is itself the risk — not just the UI — a sidecar buys time and goodwill, but the re-platform or upgrade conversation doesn't go away, it gets deferred. The honest framing for a modernization recommendation is that a sidecar and a platform upgrade are solving different problems, and treating the cheaper one as a replacement for the more expensive one is where these projects tend to under-deliver on expectations.
