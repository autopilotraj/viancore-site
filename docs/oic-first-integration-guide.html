Your First Oracle Integration (OIC) Flow: A PeopleSoft Admin's Field Guide

If you have spent years with Integration Broker, OIC will feel familiar in places and foreign in others. This guide walks through one complete flow, from an empty cloud account to a tested and monitored integration, and maps each step back to concepts a PeopleSoft admin already knows.

In Short

Oracle Integration 3 (OIC) is Oracle's cloud integration platform. A typical first flow receives a REST request from an outside system, maps the data, calls an Oracle Fusion Cloud API, and returns a clean success or error response. The building blocks are a project, two connections (a trigger and an invoke), a mapping, a scope with a fault handler, and the Observability pages for monitoring. Once you see how these parts line up with nodes, service operations, and routings, the learning curve drops fast.

01 · Why OIC Matters

Why a PeopleSoft Admin Should Learn It

Most organizations running PeopleSoft today also run at least one cloud application. Many are moving pieces of Finance, HCM, or Procurement to Oracle Fusion Cloud. The glue between those systems is increasingly OIC rather than point-to-point code or custom Integration Broker routings.

The good news is that integration thinking transfers. You already understand endpoints, message structure, authentication, transformations, error queues, and the pain of a silent failure at 2 AM. OIC packages those same ideas in a low-code designer. What changes is where things live and what they are called.

Who this is for Admins, security and compliance practitioners, and functional leads who want to read, support, or audit OIC integrations with confidence. Developer depth is not required to follow along.
02 · Concept Map

Integration Broker Ideas, Translated to OIC

These are working analogies to orient yourself, not exact equivalents. The products differ in architecture, but the mental model carries over well.

OIC conceptClosest PeopleSoft ideaWhat it does
ProjectA group of related service operations and routingsA container that holds integrations, connections, and lookups for one solution, with its own access control and monitoring view.
ConnectionNode plus its connector propertiesStores the endpoint, adapter type, and credentials for one external system. Reusable across integrations.
Trigger connectionInbound service operationStarts the integration. A REST trigger exposes the integration as a REST API that outside systems can call.
Invoke connectionOutbound routing to a target nodeSends data to the target application, such as a Fusion Cloud REST resource.
MapperTransform program or data mappingMoves and reshapes fields from the source message to the target message.
Scope and fault handlerException handling in PeopleCode or an error-handling routingGroups actions so failures inside them can be caught and handled in one place.
Activity streamAsynchronous services monitor and message detailsA step-by-step runtime record of what the integration did, including payloads at higher tracing levels.
Project export (.CAR)Project definition migrated with Application DesignerPackages the project so it can be imported into another instance.
03 · The Scenario

A Realistic First Use Case

Picture a common request: a vendor onboarding form lives in a separate request or ticketing tool. Today, someone retypes each approved vendor into Fusion Procurement. The goal is to remove that manual step.

Source system sends an approved vendor as a JSON payload
↓
OIC REST trigger receives the request and validates required fields
↓
Mapper reshapes the payload into the Fusion supplier format
↓
Fusion invoke creates the supplier through the Suppliers REST resource
↓
Response returns the new supplier ID, or a readable error the caller can act on

Supplier creation is a good learning case because it is synchronous, easy to verify in the Fusion UI, and it fails in predictable ways (duplicate names, missing required values, missing privileges). That gives you real errors to practice handling.

On the Fusion side, the Suppliers resource accepts a POST to create one supplier:

POST https://<fusion-host>/fscmRestApi/resources/11.13.18.05/suppliers
Privileges first The Fusion user behind your connection needs the roles and privileges for that REST resource. A large share of first-run failures are security, not design. Confirm access in Fusion before you blame the integration.
04 · Environment Setup

Getting a Place to Practice

A practice tenancy

If your organization does not already give you an OIC sandbox, an Oracle Cloud Free Tier account is the usual starting point. It includes a time-limited Free Trial with promotional credits on top of the Always Free services. Check Oracle's Free Tier page for the current credit amount, trial length, and eligible services before you plan your learning around it. Trial resources that are not upgraded to a paid account are reclaimed when the trial ends, so export anything you want to keep.

Creating the OIC instance

In the OCI Console, OIC lives under Developer Services › Application Integration › Integration. Create a compartment for your learning work first, then create the instance inside it. New instances are Oracle Integration 3. Generation 2 instances can no longer be created.

Standard edition
Integrations, standard adapters, recipes
Enterprise edition
Adds enterprise adapters, Process Automation, and more
Healthcare edition
Adds healthcare-specific capabilities. One-way upgrade
Instance state
Can be stopped when idle to conserve credits

Controlled access

Treat even a sandbox like production from a security standpoint. Grant OIC roles to groups, not individual users, and give people the least role they need. Developers build, monitors observe, administrators configure. This is the same separation-of-duties conversation you already have with auditors about PeopleSoft permission lists.

05 · Connections

Create the Project, Then the Two Connections

Oracle recommends building inside a project. Start there so your connections, integration, and monitoring all stay together. Connections can also be shared across projects later, which avoids maintaining duplicates.

  • 1Trigger connection (REST Adapter). Configure it with the trigger role. This is what makes your integration callable as a REST API by the source system.
  • 2Invoke connection (Oracle ERP Cloud Adapter). Point it at your Fusion host and supply the credentials for the integration user. This adapter understands Fusion business objects, which saves you from hand-building the API call.
  • 3Test each connection. Use the Test action before saving. A connection that fails here will fail inside every integration that uses it.
Admin habit worth keeping Use a dedicated integration account in Fusion, never a named person's login. When that person leaves, the integration should not break, and your access reviews stay clean.
06 · Building the Flow

From Blank Canvas to Working Integration

Create an application integration inside the project and work through it in this order:

  • 1Configure the trigger. Define the resource path, the POST method, a request sample (JSON), and a response sample. Keep the response simple: a status, the new supplier ID, and a message.
  • 2Add a scope. Place the invoke and its mapping inside a scope so you can catch failures there. More on this in the next section.
  • 3Add the Fusion invoke. Choose the supplier business object and the create operation.
  • 4Map the request. Drag source fields to target fields. Required supplier attributes typically include the supplier name, type, business relationship, and tax organization type. Confirm the exact required set in the REST API docs for your Fusion release.
  • 5Map the response. Return the created supplier ID and a success message to the caller.
  • 6Set a business identifier. Pick a tracking field such as the vendor name or source request number. This is what you will search on in monitoring, so choose something an analyst would actually know.
Hard-coded values It is tempting to hard-code a supplier type or business unit while learning. Move those into a lookup before go-live. Hard-coded values are the integration equivalent of a hard-coded SetID in PeopleCode.
07 · Fault Handling

Return Errors People Can Act On

Without error handling, a Fusion rejection comes back to the caller as a long technical fault. The person in the source system cannot do anything useful with it. OIC gives you three tools to fix that.

ToolUse it when
Scope with a default handlerYou want a catch-all for anything that fails inside a group of actions.
Throw New FaultYou want to replace the raw error with your own code, reason, and details. Best for business errors like a duplicate supplier.
Re-throw FaultYou want to pass the original error up to the global fault handler unchanged. Best for system errors you need to preserve for troubleshooting.

A practical pattern for this flow:

Scope: Create Supplier ├─ Map request ├─ Invoke Fusion (create supplier) └─ Default Handler ├─ Log the original fault details └─ Throw New Fault code: SUPPLIER_CREATE_FAILED reason: Supplier could not be created in Fusion details: (message extracted from the original fault)
Do not lose the evidence Throw New Fault replaces the original error. Log the original details first, or support teams lose the root cause. Auditors also like seeing that failed transactions leave a trace.
08 · Testing

Prove It Works, Then Prove It Fails Well

Integrations built on a REST trigger can be tested from inside the project. Once activated, you can also call the endpoint from any REST client such as Postman or curl, using the credentials the trigger's security policy expects.

curl -X POST "https://<oic-host>/ic/api/integration/v1/flows/rest/<project-path>/<resource>" \ -H "Content-Type: application/json" \ -u "<integration-user>" \ -d '{ "vendorName": "Sample Vendor LLC", "vendorType": "Supplier" }'
Copy the real endpoint The URL above is illustrative. Copy the exact endpoint from the activated integration's details in your instance rather than building it by hand.

Run at least these cases before calling it done:

  • 1Happy path. A new vendor is created and the response returns its ID. Verify the record in Fusion.
  • 2Duplicate. Send the same vendor again. You should receive your custom error, not a raw stack trace.
  • 3Missing required field. Confirm the error message names the field.
  • 4Bad credentials. Confirm the caller gets an authentication error and nothing reaches Fusion.
09 · Monitoring

Where to Look When Something Breaks

OIC has two monitoring views. The Observe page inside a project shows only that project's integrations. The Observability pages in the navigation pane show everything across the instance. Both let you filter instances by status, open an instance, and read its activity stream step by step.

  • 1Search by business identifier. This is why you set one during the build.
  • 2Open the activity stream. It shows each action, where the message went, and where it failed.
  • 3Mind the tracing level. Higher tracing captures payloads, which helps debugging but also stores data. Lower it once the flow is stable.
Compliance angle Payloads in the activity stream can include vendor names, tax details, or banking data. Treat tracing levels and data retention as a data-handling decision, not just a debugging setting. If you need longer retention for audit, OIC can push the activity stream to OCI Logging, where retention is configurable.
10 · Promotion

Moving the Work to Another Instance

When the flow is ready to move, export the project. The export produces a .CAR file that can be imported into another instance from your local machine or from a GitHub repository. If you only want to move part of a project, create a project deployment that includes the specific integrations and export that instead.

Connections do not travel with credentials Remote shared connections are not included in a project export, and local connection overrides are not exported either. Plan to reconfigure and retest every connection in the target instance. This is the same discipline as re-pointing nodes after a PeopleSoft refresh.
11 · Go-Live Checklist

Before You Call It Production-Ready

  • 1Integration user is a service account with only the Fusion privileges it needs
  • 2OIC roles are granted to groups, with build and monitor duties separated
  • 3Every invoke sits inside a scope with a fault handler
  • 4Original fault details are logged before any custom fault is thrown
  • 5A meaningful business identifier is set for tracking
  • 6Hard-coded values are moved to lookups
  • 7Tracing level is set for production, with retention reviewed against data policy
  • 8Happy path, duplicate, missing field, and bad credential tests are documented
  • 9Project export is version-controlled and connection setup steps are written down
12 · Lessons Learned

What Carries Over From PeopleSoft

Security problems look like integration problems

Just as a certificate trust issue can masquerade as a broken node ping, a missing Fusion privilege often surfaces as a vague invoke failure. Check access before redesigning the flow.

Design the error message for the person who will read it

A good integration fails in a way the business user can fix without opening a ticket. That one decision reduces support load more than any performance tuning.

Monitoring is part of the build, not an afterthought

Business identifiers, tracing levels, and retention are cheap to set during design and painful to retrofit after an audit request.

Official references

Oracle's documentation is the source of truth for screens, editions, and limits, which change between releases. Start with Oracle Integration 3 documentation and the Oracle Fusion Procurement REST API reference for your release.
